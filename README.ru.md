**Тёплый и удобный лаунчер для Vintage Story.**

Waxlight Launcher был создан и самостоятельно разрабатывается
[AmadoMuerte](https://github.com/AmadoMuerte). Это его личный независимый
проект. Разработка не связана с сотрудничеством, согласованием, одобрением или
другими отношениями с разработчиками Vintage Story.

Waxlight объединяет аккаунты, версии игры, изолированные сборки, моды, запуск
игры и статистику игрового времени в одном настольном приложении. Проект
создан с использованием Go, Wails, React, TypeScript и SQLite и поддерживает
Windows и Linux.

Waxlight не распространяет игру и не обходит её лицензирование. Для
использования требуется действующий аккаунт Vintage Story и право на
скачивание игры.

## Возможности Waxlight

* Управление несколькими аккаунтами Vintage Story, включая вход с TOTP/2FA.
* Получение списка релизов Vintage Story и установка нескольких версий игры
  одновременно.
* Создание изолированных сборок, настройки и моды которых не смешиваются.
* Просмотр Vintage Story ModDB с поиском, фильтрами, сортировкой и страницами
  модов.
* Скачивание, установка, обновление, включение, отключение и удаление модов для
  каждой сборки.
* Проверка выбранного аккаунта и версии игры перед запуском.
* Запуск и остановка игры, сохранение логов и предотвращение конфликтующих
  запусков.
* Учёт отдельных игровых сессий, общего времени в игре и времени по каждой
  сборке.
* Отображение текущих и завершённых загрузок и других длительных операций.
* Поддержка нескольких языков интерфейса с сохранением выбранного языка.

Каждый релиз также содержит файл `SHA256SUMS`. Проверить скачанные файлы в
Linux можно командой:

```bash
sha256sum --check SHA256SUMS --ignore-missing
```

### Установка в Windows

Скачайте и запустите установщик. Также можно распаковать портативный ZIP-архив
и запустить `waxlight.exe`.

Для работы Waxlight требуется Microsoft Edge WebView2 Runtime. Он уже входит в
современные версии Windows, а при его отсутствии установщик Waxlight может
установить его автоматически.

Ранние неподписанные сборки могут вызывать предупреждение Microsoft Defender
SmartScreen. Перед запуском убедитесь, что файл скачан со страницы Releases
этого репозитория, и проверьте его контрольную сумму.

### Установка в Debian и Ubuntu

```bash
sudo apt install ./Waxlight-Launcher-v0.1.2-linux-amd64.deb
```

### Установка в Fedora

```bash
sudo dnf install ./Waxlight-Launcher-v0.1.2-linux-amd64.rpm
```

### Портативная установка в Linux

Для работы портативной сборки требуются GTK 3 и WebKitGTK 4.1. Установите их
через пакетный менеджер своего дистрибутива, затем распакуйте архив и запустите
Waxlight:

```bash
tar -xzf Waxlight-Launcher-v0.1.2-linux-amd64.tar.gz
cd Waxlight-Launcher-v0.1.2-linux-amd64
./waxlight
```

AppImage пока не публикуется. Для первого релиза портативный архив является
универсальным вариантом для Linux-дистрибутивов.

## Первый запуск

1. Откройте раздел **Аккаунты** и войдите в аккаунт Vintage Story.
2. Откройте раздел **Версии игры** и установите поддерживаемую версию.
3. Создайте сборку в разделе **Библиотека** и выберите для неё версию игры и
   аккаунт.
4. При необходимости установите моды в разделе **Моды**.
5. Выберите сборку и нажмите **Запустить**.

Waxlight хранит локальную базу данных, скачанные файлы и настройки в
пользовательской папке конфигурации операционной системы:

* Linux: `~/.config/waxlight/`
* Windows: `%AppData%\waxlight\`

Перед резервным копированием или переносом этой папки остановите все запущенные
игры.

Никогда не прикладывайте к публичным issue всю папку данных, файлы
`clientsettings.json` из сборок или логи. Постоянные данные сессий находятся в
системном хранилище учётных данных и не переносятся вместе с папкой данных
Waxlight.

## Языки интерфейса

Сейчас Waxlight включает:

* английский;
* русский.

Выбранный язык сохраняется в настройках приложения и восстанавливается при
следующем запуске Waxlight.

Файлы переводов находятся в:

```text
frontend/src/i18n/locales/
```

Для каждого языка используется один JSON-файл со стабильными ключами в
`snake_case`:

```text
en.json
ru.json
```

Английский файл является основным источником ключей и резервным языком.
Участники проекта могут исправлять существующие переводы и добавлять новые.

При редактировании переводов:

* переводите только значения;
* не переименовывайте существующие ключи;
* сохраняйте выражения интерполяции, например `{{name}}`;
* сохраняйте окончания plural-ключей: `_one`, `_few`, `_many` и `_other`;
* не переводите технические названия, пути, URL и идентификаторы версий.

Проверить файлы переводов можно командой:

```bash
npm run check:i18n --prefix frontend
```

Полный порядок внесения изменений описан в
[CONTRIBUTING.md](CONTRIBUTING.md).

## Состояние проекта

Waxlight активно разрабатывается. Версии `0.1.x` следует считать ранними
релизами: создавайте резервные копии важных сохранений, проверяйте совместимость
перед установкой модов и учитывайте, что интерфейс и модель локальных данных
могут изменяться.

Авторизация изолирована за клиентом Go backend. Пароли и TOTP-коды никогда не
сохраняются.

Постоянные ключи и подписи сессий хранятся через Secret Service в Linux и
Windows Credential Manager в Windows. В production-сборках отсутствует
незашифрованный резервный способ хранения.

React получает только разрешённые DTO аккаунтов и не может получить исходные
данные сессий через Wails API.

Перед запуском игры четыре поля, необходимые Vintage Story, записываются в
`clientsettings.json` соответствующей сборки только после проверки сессии.
Waxlight удаляет их после обычного завершения игры и после ошибки запуска, а
также очищает оставшиеся поля при следующем запуске приложения после сбоя.

Удаление аккаунта очищает связанные настройки сборок, однако локальное удаление
не может гарантированно отозвать уже выданную серверную сессию. Подробная модель
и ограничения описаны в
[документации по авторизации](docs/authentication.md) и
[политике безопасности](SECURITY.md).

Скачивание версий игры поддерживает отображение прогресса, отмену, продолжение
загрузки там, где это возможно, и проверку контрольных сумм. Подробности
описаны в [документации по версиям игры](docs/game-versions.md).

## Сборка из исходного кода

### Требования

* Go 1.24 или новее;
* Node.js 22 и npm;
* Wails CLI 2.11;
* компилятор C;
* [системные зависимости Wails](https://wails.io/docs/gettingstarted/installation/)
  для вашей операционной системы;
* в Linux — пакеты разработки GTK 3 и WebKitGTK 4.1.

Клонирование и проверка проекта:

```bash
git clone https://github.com/AmadoMuerte/Waxlight-launcher.git
cd Waxlight-launcher
npm ci --include=dev --prefix frontend
go install golang.org/x/vuln/cmd/govulncheck@v1.6.0
make release-check
```

Запуск настольного приложения с автоматическим обновлением:

```bash
go install github.com/wailsapp/wails/v2/cmd/wails@v2.11.0
cd cmd/waxlight
wails dev
```

Сборка production-приложения:

```bash
make wails-build
```

Команду Wails необходимо запускать из папки `cmd/waxlight`. Корневой `Makefile`
предоставляет сокращённые команды для стандартных операций.

Обычный `go build` без desktop-тегов Waxlight не создаёт поддерживаемую
графическую сборку.

Полезные команды:

```bash
make test                 # Тесты Go и frontend
make vet                  # Статический анализ Go
make frontend             # Production-сборка TypeScript и Vite
make package-linux        # Локальная сборка .deb, .rpm и портативного архива
make release-check        # Полная проверка перед релизом
make security             # Проверки уязвимостей и запрещённых шаблонов
```

## Архитектура

Go-приложение использует слоистую архитектуру:

```text
Presentation (Wails) -> Application -> Domain
Infrastructure -------> Application / Domain
```

React frontend взаимодействует со сгенерированными Wails bindings через общий
API-слой.

Бизнес-правила, загрузки, изменение файловой системы, авторизация, управление
процессами и подсчёт игрового времени остаются в Go, а не в React-компонентах.

Основные папки:

```text
cmd/waxlight/             Точка входа desktop-приложения и конфигурация Wails
internal/domain/          Основные модели и доменные ошибки
internal/application/     Сценарии использования и интерфейсы сервисов
internal/infrastructure/  SQLite, HTTP, файловая система, credentials, процессы
internal/presentation/    Wails-контроллеры и DTO
frontend/src/             Интерфейс на React и TypeScript
frontend/src/i18n/        Локализация интерфейса
packaging/                Метаданные desktop-приложения и Linux-пакетов
scripts/                  Воспроизводимые скрипты релиза
.github/workflows/        CI и автоматизация релизов
```

## Участие в разработке

Предложения и изменения приветствуются. Перед созданием pull request:

1. Прочитайте [CONTRIBUTING.md](CONTRIBUTING.md).
2. Создайте отдельную ветку от `main`.
3. Не размещайте бизнес-логику в React-компонентах и Wails-контроллерах.
4. Добавьте или обновите тесты для изменённого поведения.
5. Выполните `make release-check`.
6. Опишите пользовательские изменения и проведённое тестирование в pull
   request.

Используйте шаблоны issue для воспроизводимых ошибок и конкретных предложений
функциональности.

Для сообщений об уязвимостях или случайном раскрытии учётных данных следуйте
[SECURITY.md](SECURITY.md), а не создавайте публичный issue.

Переводы также можно улучшать и дополнять. Поддерживайте набор ключей в
соответствии с `frontend/src/i18n/locales/en.json` и запускайте проверку i18n
перед отправкой pull request.

## Релизы

Каждый push и pull request в `main` запускает:

* тесты;
* статический анализ;
* сборку frontend;
* нативные интеграционные тесты системного хранилища учётных данных в Linux и
  Windows;
* поиск уязвимостей и секретов;
* Linux-сборку Wails.

Push тега семантической версии, например `v0.1.0`, запускает процесс релиза,
который:

1. проверяет соответствие тега версии приложения;
2. собирает Windows- и Linux-артефакты на нативных GitHub runners;
3. проверяет созданные пакеты;
4. создаёт `SHA256SUMS`;
5. публикует GitHub Release с автоматически сформированными примечаниями.

GitHub Actions закреплены за неизменяемыми commit hash, а релизные файлы
получают контрольные суммы SHA-256.

Подписание релизов сейчас не настроено. Опубликованные контрольные суммы
позволяют проверить целостность файлов после получения `SHA256SUMS`, но не
заменяют аутентифицированную цепочку подписей.

Перед созданием тега обновите версию в обоих конфигурационных файлах Wails.
Существующие релизные теги нельзя перемещать.
