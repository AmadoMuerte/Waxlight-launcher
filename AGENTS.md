## 1. Назначение проекта

Проект Waxlight Launcher представляет собой современный неофициальный кроссплатформенный лаунчер для Vintage Story.

Лаунчер должен предоставлять пользователю единый интерфейс для:

* авторизации в Vintage Story;
* управления несколькими аккаунтами;
* установки разных версий игры;
* создания независимых игровых сборок;
* установки и управления модами;
* поиска модов через каталог;
* запуска игры;
* отслеживания игрового времени;
* управления настройками отдельных сборок.

Основные поддерживаемые платформы:

* Linux;
* Windows.

Основной приоритет проекта — надёжность, понятная архитектура, строгая типизация и удобство дальнейшего расширения.

# 2. Технологический стек

## Backend

* Go;
* Wails v2;
* SQLite для локального хранения данных;
* стандартная библиотека Go везде, где она достаточна;
* сторонние библиотеки только при наличии понятной необходимости.

## Frontend

* React;
* TypeScript;
* Vite;
* CSS Modules, Tailwind CSS или другой заранее выбранный единый подход к стилизации;
* React Router для навигации;
* Zustand либо React Context для глобального состояния;
* TanStack Query для серверного и асинхронного состояния, если это будет оправдано.

## Общие требования

* Backend и frontend должны быть логически разделены.
* Бизнес-логика не должна находиться в React-компонентах.
* Бизнес-логика не должна быть напрямую привязана к Wails.
* Wails используется как транспортный слой между Go и frontend.
* Доменные структуры должны иметь чёткие типы.
* Не использовать `any` в TypeScript без крайней необходимости.
* Не использовать глобальное изменяемое состояние в Go.
* Следовать принципам DRY, KISS и разделения ответственности.

# 3. Основные термины

## Account

Авторизованный аккаунт Vintage Story.

Один пользователь лаунчера может сохранить несколько аккаунтов и переключаться между ними.

## Game Version

Конкретная версия Vintage Story, доступная для установки.

## Instance

Независимая сборка игры.

Каждый instance содержит:

* название;
* выбранную версию игры;
* отдельную директорию;
* собственный набор модов;
* собственные настройки;
* собственные параметры запуска;
* статистику игрового времени;
* выбранный аккаунт по умолчанию.

В интерфейсе instance может называться «Сборка».

## Mod

Модификация Vintage Story.

Мод может быть:

* доступен в удалённом каталоге;
* установлен в конкретный instance;
* включён;
* отключён;
* обновлён;
* несовместим с выбранной версией игры.

## Play Session

Один сеанс игры от момента успешного запуска процесса Vintage Story до завершения процесса.

# 4. Основные функциональные требования

## 4.1 Управление аккаунтами

Лаунчер должен поддерживать:

* авторизацию через лаунчер;
* сохранение нескольких аккаунтов;
* безопасное хранение токенов;
* переключение активного аккаунта;
* выход из отдельного аккаунта;
* повторную авторизацию;
* автоматическое восстановление сессии;
* выбор аккаунта перед запуском игры;
* назначение аккаунта по умолчанию для отдельного instance.

Запрещено хранить пароли в открытом виде.

Предпочтительный подход:

* хранить refresh token или другой официальный токен авторизации;
* использовать системное защищённое хранилище, если это возможно;
* предусмотреть абстракцию `CredentialStore`;
* иметь fallback-хранилище только при явном согласии пользователя.

---

## 4.2 Управление версиями игры

Лаунчер должен позволять:

* получать список доступных версий Vintage Story;
* устанавливать выбранную версию;
* хранить несколько версий одновременно;
* проверять наличие установленной версии;
* проверять целостность файлов;
* переустанавливать повреждённую версию;
* удалять неиспользуемые версии;
* показывать прогресс загрузки;
* показывать скорость загрузки;
* поддерживать отмену загрузки;
* возобновлять загрузку, если это технически возможно.

Установленные версии игры не должны дублироваться для каждого instance без необходимости.

Следует использовать общее хранилище игровых версий и создавать instance поверх выбранной версии.

Если Vintage Story требует физического копирования файлов для изоляции сборок, решение должно быть вынесено в отдельную стратегию:

```go
type InstanceProvisioner interface {
    Provision(ctx context.Context, version GameVersion, targetPath string) error
}
```

Реализация может использовать:

* копирование;
* жёсткие ссылки;
* символические ссылки;
* общий runtime с отдельными пользовательскими данными.

Выбор реализации зависит от поведения игры и платформы.

---

## 4.3 Управление сборками

Пользователь должен иметь возможность:

* создать новую сборку;
* выбрать название сборки;
* выбрать версию Vintage Story;
* выбрать директорию;
* выбрать аккаунт по умолчанию;
* клонировать сборку;
* переименовать сборку;
* удалить сборку;
* изменить версию игры;
* открыть директорию сборки;
* открыть директорию модов;
* добавить пользовательские аргументы запуска;
* включить или отключить отдельные моды;
* экспортировать конфигурацию сборки;
* импортировать конфигурацию сборки.

Каждая сборка должна быть изолирована от остальных.

Изменение модов или настроек одной сборки не должно влиять на другие сборки.

---

## 4.4 Каталог модов

Лаунчер должен предоставлять каталог модов.

Каталог должен поддерживать:

* список модов;
* пагинацию;
* бесконечную прокрутку либо обычное переключение страниц;
* поиск по названию;
* поиск по описанию;
* фильтрацию по версии игры;
* фильтрацию по категории;
* фильтрацию по автору;
* сортировку по популярности;
* сортировку по дате обновления;
* сортировку по количеству загрузок;
* переход на страницу конкретного мода;
* просмотр описания;
* просмотр изображений;
* просмотр автора;
* просмотр доступных версий;
* просмотр совместимости;
* установку подходящей версии;
* обновление установленного мода;
* удаление мода.

Удалённый API каталога не должен вызываться напрямую из React-компонентов.

Frontend должен обращаться к backend через сервис каталога.

Backend отвечает за:

* HTTP-запросы;
* кеширование;
* преобразование данных;
* обработку ошибок;
* скачивание файлов;
* проверку целостности;
* установку модов.

---

## 4.5 Установленные моды

Для каждого instance должен отображаться список установленных модов.

Для каждого мода необходимо показывать:

* название;
* версию;
* автора;
* статус;
* совместимость;
* наличие обновления;
* размер;
* дату установки;
* источник установки.

Доступные действия:

* включить;
* отключить;
* обновить;
* удалить;
* открыть страницу мода;
* открыть файл мода;
* проверить совместимость.

Следует различать:

* данные удалённого каталога;
* установленный файл;
* запись в локальной базе;
* фактическое состояние файловой системы.

Файловая система считается источником истины для факта наличия файла, а база данных — источником метаданных лаунчера.

---

## 4.6 Запуск игры

Лаунчер должен:

* проверить выбранный аккаунт;
* проверить наличие версии игры;
* проверить состояние instance;
* подготовить параметры запуска;
* запустить процесс Vintage Story;
* отслеживать состояние процесса;
* получать stdout и stderr;
* записывать лог запуска;
* блокировать повторный запуск одного instance, если это необходимо;
* корректно обрабатывать завершение игры;
* сохранять игровое время;
* показывать текущий статус сборки.

Возможные статусы:

```go
type InstanceStatus string

const (
    InstanceStatusIdle       InstanceStatus = "idle"
    InstanceStatusPreparing  InstanceStatus = "preparing"
    InstanceStatusRunning    InstanceStatus = "running"
    InstanceStatusStopping   InstanceStatus = "stopping"
    InstanceStatusError      InstanceStatus = "error"
)
```

Запуск должен выполняться через отдельный сервис, не через Wails-контроллер напрямую.

---

## 4.7 Учёт игрового времени

Лаунчер должен отслеживать игровое время:

* для каждой игровой сессии;
* для каждого instance;
* для каждого аккаунта;
* для каждой версии игры;
* суммарно по всем instance.

Под одной игровой сессией понимается время существования успешно запущенного процесса игры.

Следует сохранять:

* время запуска;
* время завершения;
* продолжительность;
* instance;
* аккаунт;
* версию игры;
* код завершения процесса;
* признак аварийного завершения.

Продолжительность должна вычисляться backend, а не frontend.

Минимальная модель:

```go
type PlaySession struct {
    ID         string
    InstanceID string
    AccountID  string
    VersionID  string
    StartedAt  time.Time
    EndedAt    *time.Time
    Duration   time.Duration
    ExitCode   *int
    Crashed    bool
}
```

Если лаунчер аварийно закрылся во время работы игры, при следующем запуске необходимо обработать незавершённую сессию.

Domain не должен зависеть от:

* Wails;
* React;
* SQLite;
* HTTP-клиентов;
* конкретной операционной системы.

# 7. Backend

## 7.1 Domain Layer

Domain содержит основные сущности и правила предметной области.

Примеры сущностей:

* `Account`;
* `GameVersion`;
* `Instance`;
* `InstalledMod`;
* `ModRelease`;
* `PlaySession`;
* `LaunchConfiguration`.

Domain не должен выполнять:

* SQL-запросы;
* HTTP-запросы;
* работу с Wails;
* работу с React;
* прямую работу с файловой системой.

Пример:

```go
type Instance struct {
    ID               string
    Name             string
    GameVersionID    string
    DefaultAccountID *string
    Directory        string
    CreatedAt        time.Time
    UpdatedAt        time.Time
}
```

Валидация доменных данных должна находиться рядом с доменной моделью или в соответствующем application-сервисе.

---

## 7.2 Application Layer

Application содержит сценарии использования.

Примеры:

* `CreateInstance`;
* `CloneInstance`;
* `InstallGameVersion`;
* `InstallMod`;
* `UpdateMod`;
* `AuthenticateAccount`;
* `LaunchGame`;
* `FinishPlaySession`;
* `GetPlaytimeStatistics`.

Application-сервис координирует domain и infrastructure через интерфейсы.

Пример:

```go
type InstanceRepository interface {
    Create(ctx context.Context, instance *instance.Instance) error
    GetByID(ctx context.Context, id string) (*instance.Instance, error)
    List(ctx context.Context) ([]instance.Instance, error)
    Update(ctx context.Context, instance *instance.Instance) error
    Delete(ctx context.Context, id string) error
}
```

Интерфейс должен объявляться в пакете, который его использует, а не в пакете конкретной реализации.

---

## 7.3 Infrastructure Layer

Infrastructure содержит конкретные реализации:

* SQLite-репозитории;
* HTTP-клиенты;
* клиент API Vintage Story;
* клиент каталога модов;
* файловое хранилище;
* загрузчик файлов;
* системное хранилище секретов;
* запуск процессов;
* платформенные реализации для Linux и Windows.

Примеры:

```text
SQLiteInstanceRepository
VintageStoryAuthClient
VintageStoryVersionClient
ModCatalogHTTPClient
HTTPDownloader
SystemCredentialStore
WindowsProcessLauncher
LinuxProcessLauncher
```

Infrastructure не должна содержать UI-логику.

---

## 7.4 Presentation Layer

Presentation содержит методы, доступные frontend через Wails.

Контроллеры должны:

* принимать DTO;
* выполнять базовую проверку входных данных;
* вызывать application-сервис;
* преобразовывать результат в DTO;
* возвращать понятные ошибки.

Контроллеры не должны:

* самостоятельно выполнять SQL;
* скачивать файлы;
* запускать игру;
* работать с токенами;
* содержать бизнес-правила.

Плохо:

```go
func (c *InstanceController) CreateInstance(name string) error {
    db.Exec(...)
    os.MkdirAll(...)
    // другая бизнес-логика
    return nil
}
```

Хорошо:

```go
func (c *InstanceController) CreateInstance(
    request CreateInstanceRequest,
) (InstanceDTO, error) {
    result, err := c.createInstance.Execute(c.ctx, request.ToCommand())
    if err != nil {
        return InstanceDTO{}, mapError(err)
    }

    return NewInstanceDTO(result), nil
}
```

## 8.1 React-компоненты

Компоненты должны быть небольшими и иметь одну ответственность.

Следует разделять:

* UI-компоненты;
* контейнеры;
* бизнес-действия;
* работу с API;
* состояние.

Компонент страницы не должен содержать всю логику страницы.

Плохо:

```tsx
function ModsPage() {
    // загрузка модов
    // фильтры
    // пагинация
    // установка
    // удаление
    // уведомления
    // рендеринг всей страницы
}
```

Хорошо:

```tsx
function ModsPage() {
    return (
        <PageLayout>
            <ModFilters />
            <ModCatalog />
        </PageLayout>
    )
}
```

## 8.2 Вызовы Wails

Все вызовы сгенерированных Wails bindings должны быть обёрнуты в единый frontend API-слой.

Плохо:

```tsx
import { InstallMod } from "../../../wailsjs/go/main/App"
```

в каждом компоненте.

Хорошо:

```ts
export const modsApi = {
    list: (params: ModSearchParams) => ModController.Search(params),
    install: (request: InstallModRequest) =>
        ModController.Install(request),
}
```

Компоненты и hooks должны использовать `modsApi`, а не напрямую Wails bindings.

Это позволит:

* менять transport layer;
* мокировать API в тестах;
* централизованно обрабатывать ошибки;
* избегать дублирования.

## 8.3 Состояние frontend

Разделять:

### Локальное UI-состояние

Примеры:

* выбранная вкладка;
* состояние поля ввода;
* раскрыта ли боковая панель.

Использовать локальный `useState`.

Примеры:

* активный аккаунт;
* активный instance;
* тема;
* настройки интерфейса.

Использовать Zustand или Context.

### Асинхронное состояние

Примеры:

* список модов;
* список версий;
* список аккаунтов;
* статистика;
* данные сборок.

Использовать единый слой hooks и, при необходимости, TanStack Query.

Не хранить один и тот же набор данных одновременно в нескольких store.

# 9. DRY

DRY означает отсутствие дублирования знаний, а не механическое объединение любого похожего кода.

Необходимо избегать дублирования:

* бизнес-правил;
* SQL-запросов;
* API-вызовов;
* преобразования ошибок;
* путей директорий;
* строковых статусов;
* моделей запросов;
* логики загрузки;
* логики вычисления игрового времени;
* UI-компонентов;
* фильтров;
* форматирования дат и размеров файлов.

# 10. DTO и модели

Не следует без необходимости передавать domain-сущности напрямую во frontend.

Использовать DTO:

```go
type InstanceDTO struct {
    ID               string  `json:"id"`
    Name             string  `json:"name"`

    DefaultAccountID *string `json:"defaultAccountId,omitempty"`
    InstalledMods    int     `json:"installedMods"`

```

DTO отвечает потребностям интерфейса и может содержать агрегированные значения.

Domain-модель не должна изменяться только ради удобства отображения frontend.

# 12. Обработка ошибок

Backend должен использовать типизированные ошибки.

Пример:

```go
var (
    ErrAccountNotFound        = errors.New("account not found")
    ErrInstanceNotFound       = errors.New("instance not found")
    ErrVersionNotInstalled    = errors.New("game version not installed")
    ErrAuthenticationRequired = errors.New("authentication required")
)
```

Для frontend ошибка должна преобразовываться в структуру:

```go
type AppErrorDTO struct {
    Code       string            `json:"code"`
    Message    string            `json:"message"`
    Details    map[string]string `json:"details,omitempty"`
    Retryable  bool              `json:"retryable"`
}
```

Frontend не должен определять тип ошибки путём анализа текста сообщения.

Плохо:

```ts
if (error.message.includes("not found")) {
    // ...
}
```

Хорошо:

```ts
if (error.code === "INSTANCE_NOT_FOUND") {
    // ...
}
```

# 22. Правила для агента

Перед изменением кода агент обязан:

1. определить затрагиваемый слой;
2. найти существующий сервис или компонент;
3. проверить, можно ли расширить существующую абстракцию;
4. не создавать дублирующий модуль;
5. проверить связанные тесты;
6. сохранить обратную совместимость, если иное не указано.

Агент не должен:

* помещать бизнес-логику в Wails-контроллеры;
* помещать бизнес-логику в React-компоненты;
* обращаться к SQLite из presentation-слоя;
* обращаться к Wails bindings из произвольных компонентов;
* дублировать DTO;
* создавать новый downloader для каждой функции;
* использовать `any` без объяснения;
* игнорировать ошибки;
* использовать `panic` для штатных ошибок;
* жёстко прописывать пользовательские пути;
* жёстко прописывать URL в UI;
* смешивать платформенный код;
* создавать огромные файлы и компоненты.

# 23. Правила внесения изменений

Каждое изменение должно:

* решать одну понятную задачу;
* сохранять архитектурные границы;
* не создавать скрытых зависимостей;
* иметь понятные имена;
* сопровождаться тестами для критической логики;
* обрабатывать ошибки;
* поддерживать отмену длительных операций;
* работать на Linux и Windows либо иметь платформенную реализацию;
* не дублировать существующую функциональность.

Перед созданием новой абстракции следует проверить, действительно ли существует повторяющееся знание.

Не создавать интерфейс только ради интерфейса.

Интерфейс оправдан, когда:

* существует несколько реализаций;
* зависимость нужно заменить в тестах;

* игровое время считается backend;
* длительные операции отменяемы;
* ошибки имеют коды;
* frontend не содержит секретов;
* повторяющаяся логика вынесена в общие модули;
* проект собирается на Linux и Windows.

# 27. Базовый архитектурный принцип

Основная логика проекта должна находиться в независимом Go-ядре.

Wails является адаптером, а не центром приложения.

React является интерфейсом, а не местом хранения бизнес-правил.

SQLite является реализацией хранилища, а не источником архитектуры.

Структура проекта должна позволять в будущем добавить:

* CLI;
* другой desktop UI;
* сервер синхронизации;
* облачное резервное копирование;
* поддержку новых платформ;
* другие источники модов;

без переписывания основного доменного ядра.
